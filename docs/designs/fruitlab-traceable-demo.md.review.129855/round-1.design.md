## Problem Statement

项目要交付一个可独立运行的水果商城 demo。它必须同时证明两件事：

1. 学员可以完成“浏览 -> 下单 -> 查单”的真实闭环。
2. 学员能从留下的人工产物中看出 GStack 八环分别做了什么、哪个门禁真正
   拦下过问题，以及这些证据如何对应到最终实现。

价值不在水果商城本身，而在一份能复现、能核对的流程证据包。目标是 Hackathon
或教学演示，不是生产商城、创业产品，也不是长期可防御的 SaaS。

## What Makes This Cool

普通教学仓库只能证明“代码最后能跑”。这个交付物的“哇”点是：页面、流程产物和
门禁记录能互相对上。学员看到的不是一段经过美化的成功故事，而是一条带有真实
判断、失败候选、否决理由和证据链接的构建轨迹。

必须同时成立：

- demo 本身可在干净目录中完成浏览、下单、查单。
- 八环各有可定位的产物，证据索引能把它们串起来。
- 至少记录一次真实门禁事件；如果整个流程没有发生阻断，就明确写“未发生阻断”，
  并同步降低演示承诺，不能补造一个。

## Constraints

- 这是 Hackathon / demo 教学交付物，不按生产系统设计。
- 功能范围只覆盖 10 种水果的浏览、下单和按订单号查询。
- 不使用数据库、登录、用户身份、管理员后台或线上部署。
- 运行状态只放在浏览器内存或 `localStorage`，不引入服务端依赖。
- 交付包必须能复制到干净目录，按固定步骤启动并复现核心流程。
- 证据必须来自实际流程产物；缺失、失败、未运行都要如实标记。
- “学员能理解门禁价值”仍未经过真实用户观察，不能写成已验证结论。
- 不为三年后的防御性做过度设计，不增加自动证据链校验器或可视化回放面板。

## Premises

1. 成功标准是“可运行闭环 + 可追溯证据”，不是功能数量或视觉复杂度。
2. 方案 A 足以支撑本次教学演示，额外自动化只在证据确实容易错位时升级。
3. 静态页面加本地存储符合“无数据库、独立运行”的约束。
4. 八环产物应保留原生格式，不复制成一套容易与原件漂移的摘要。
5. 证据索引只负责定位和解释，不能替代 `review.md`、`qa-report.md` 等原始产物。
6. P5 的最终验证来自一次外部学员观察；没有观察就保持 `UNVERIFIED`。

## Approaches Considered

### Approach A: 最小可信证据包

静态商城页面加浏览器本地存储，配一份固定启动说明和一个证据索引，把八环产物、
真实门禁事件及决策依据串起来。文件少、风险低、最符合干净目录独立运行的要求。

### Approach B: 自动校验证据链

在 A 上增加机器可读清单和校验脚本。它能减少证据错位，但会增加清单、脚本和维护
成本，把注意力从教学流程转向工具建设。本版不采用；只有 QA 证明人工索引频繁
失准时才升级。

### Approach C: 交互式流程回放

增加只读教学面板，用可视化方式回放八环和证据关系。演示冲击力最强，但工作量最大
且容易让学员关注演示 UI 而不是真实流程证据。本版明确排除。

## Recommended Approach

采用方案 A：最小可信证据包。

### 1. Runtime slice

交付一个无构建步骤的静态单页商城：

- 固定数据集包含 10 种水果，名称、单价、单位和简短描述均可直接检查。
- 商品列表支持加入购物车、调整数量和移除。
- 结账生成可读订单号，订单包含商品快照、数量、金额和创建时间。
- 查询页按订单号找到本浏览器中创建的订单；空输入、未知订单号和重复订单号都要
  有明确反馈。
- 订单保存在 `localStorage`，刷新后仍可查询；清空浏览器存储后允许丢失，这是
  demo 的已知边界。
- 不加载后端 API、第三方账号或远程数据；断网也应能完成核心闭环。

设计不追求生产级购物车、库存并发、支付或履约。浏览器控制台无未处理错误，以及
核心流程可重复完成，比增加边界功能更重要。

### 2. Evidence contract

在仓库中维护一份人工可读的 `evidence/index.md`，逐环列出：

| 字段 | 用途 |
| --- | --- |
| Ring | office-hours、spec、autoplan、build、review、qa、ship、retro |
| Artifact | 原始产物的仓库相对路径 |
| Produced by | 实际执行的技能或步骤 |
| Gate result | PASS、BLOCKED、NOT_RUN 或 NOT_APPLICABLE，只按事实填写 |
| Evidence | 可定位的行号、章节、命令输出或决策记录链接 |
| Note | 证据缺口、人工判断或未验证事项 |

索引只引用原始产物，不复制其结论。索引中的每个路径必须实际存在；未运行环节标为
`NOT_RUN`，不能为了凑满八行写成 `PASS`。

### 3. Gate event protocol

实际发生门禁阻断时，在 `evidence/gate-events/` 下新增一份短记录，包含：

- 当时尝试通过的内容。
- 哪个门禁、依据什么规则拦下。
- 原始证据路径和关键摘录。
- 修改后的处理方式。
- 这次阻断如何影响后续产物。

如果八环执行完仍没有真实阻断，创建 `evidence/gate-events/no-blocking-event.md`，
列出检查过但没有阻断的候选，并明确说明本包没有“门禁拦截”样本。不得把普通建议、
未执行的检查或事后发现包装成当时发生的阻断。

### 4. Packaging and narrative

仓库根目录的 `README.md` 负责三件事：

1. 用固定步骤启动 demo。
2. 给出“浏览 -> 下单 -> 查单”的验收脚本。
3. 指向 `evidence/index.md`，说明八环顺序和原始产物位置。

展示时先跑闭环，再打开证据索引，最后只选一条最有价值的门禁记录解释“为什么流程
改变了结果”。不把八环当成八个孤立文件逐页朗读。

### Expected artifact map

最终交付包至少应包含：

```text
index.html
assets/
README.md
OFFICE_HOURS.md
docs/designs/fruitlab-traceable-demo.md
SPEC.md
decisions/                 # autoplan 决策记录，保持其原生格式
review.md
qa-report.md
VERSION
CHANGELOG.md
retro.md
evidence/
  index.md
  gate-events/
  learner-check.md
```

这只是最小定位图，不授权为了凑文件而制造空壳产物。某环节没有实际输出时，应在
索引中说明原因，而不是放入无内容的占位文件。

## Open Questions

1. 第一次外部学员观察尚未安排；在完成前，P5 保持 `UNVERIFIED`。
2. 八环中是否会出现真实阻断目前未知。处理规则已经确定，但具体发生在哪一环只能在
   实际执行后记录。
3. 学员最容易被哪类证据说服尚未观察；当前选择人工索引，不做自动校验或可视化回放。

## Success Criteria

核心闭环：

- 在干净目录中按 README 启动后，10 种水果都能被看到并加入购物车。
- 能在一次会话中完成下单，得到一个可复制、可再次查询的订单号。
- 刷新页面后，同一浏览器仍能按订单号查到该订单。
- 空订单号、错误订单号和异常数量都有明确、可理解的反馈。
- 核心流程不依赖网络、数据库、登录或管理员操作。

证据链：

- `evidence/index.md` 覆盖八环，每行指向实际存在的原始产物。
- 每个 `PASS`、`BLOCKED`、`NOT_RUN` 状态都能由链接内容或命令输出复核。
- 至少有一条真实门禁事件；若没有，存在诚实的 `no-blocking-event.md`。
- `review.md`、`qa-report.md` 与证据索引中的结论不冲突。
- 将交付包复制到全新目录后，不依赖原目录缓存、隐藏配置或外部文件。

教学验证：

- 一名未参与构建的学员能仅凭 README 和证据索引指出至少一个门禁的作用。
- 学员卡住的位置与时间被记录，不把失败样本删掉。
- 没有外部观察时，文档和汇报都明确写 `UNVERIFIED`，不宣称教学价值已经成立。

## Distribution Plan

交付形式是可压缩、可直接复制的本地目录或仓库压缩包，不部署线上服务。接收方解压
后按 `README.md` 启动静态页面即可。没有 CI/CD、发布流水线或托管依赖。

`VERSION` 和 `CHANGELOG.md` 只服务于八环演示，不承诺语义化版本兼容。分享时应给出
实际提交哈希或压缩包时间，避免同名包无法区分。

## Dependencies

- 现代 Chromium 浏览器和本地静态文件访问能力。
- 用户在每个环结束后的明确批准，流程不得自动跨环。
- review、QA 和 ship 的真实执行结果；没有执行就没有对应证据。
- 至少一次外部学员观察，用于验证教学价值假设。
- 真实门禁事件无法预先保证，因此证据包必须支持“没有发生阻断”的诚实分支。

## Next Steps

1. 在进入 spec 前冻结证据索引字段、八环产物名称和“无阻断”记录规则。
2. 由 spec 把核心闭环、异常路径、验收标准和不可做项写成可执行规格。
3. 实现静态商城、README 和人工证据索引骨架，不添加数据库或后台。
4. 依次执行 autoplan、build、review、qa、ship、retro，并在每一步写入实际结果。
5. 把交付包复制到全新目录，按 README 完整跑通浏览、下单、查单。
6. 找一名未参与构建的学员做一次证据理解测试，记录原话、卡点和是否成功。

## The Assignment

在进入 spec 前，找一名未参与本项目的学员，用 5 分钟只读这份设计文档，然后请其
回答两个问题：

1. 这份包用什么证据证明流程真的拦下过问题？
2. 如果没有任何阻断，它应该怎样诚实说明？

把对方原话、卡住的位置和所需提示记录到 `evidence/learner-check.md`。如果暂时找不到
学员，也要建立该文件并写明 `UNVERIFIED: no external learner observed`，不能编造
反馈。

- 你接受“当前卖点是流程可见性和证据链，不是水果商城本身，也不是长期技术护城河”
  这一判断，说明你愿意按教学交付物优化，而不是把它包装成不属于它的产品。
